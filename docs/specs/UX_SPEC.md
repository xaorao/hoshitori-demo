# User-experience architecture

Scope: interface architecture for Track 2. Status: DESIGNED; the layer-1 budget and accessibility checks were run on a static mock built from the card contract (E11) and changed two contract numbers (CF-17, CF-18). Product rules: description 2.4, 2.4c, 4.25; contract sections 22, 33, 35, 38, 44, 49, 54. This document states how those rules are made enforceable in code; it adds no feature.

## 1. Architectural rule: the page is a function of typed view models

Every layer-1 string reaches the page through a **view model** produced by the server from stored records. The renderer has no free-text input of its own. Consequences, each testable:

- The card view model has exactly the fields of the card contract (`headline`, `state_chip` from a closed list, `uncertainty_chip` from a closed list, four slots for the featured card, `meta`, one `control`, `trust_phrase` from the five-phrase list, `origin_count`). A field that can carry a verdict word, a probability or a stance does not exist on the unchecked-row and preliminary-page view models (contract 35.2: absence by construction, then a lint).
- Strings are produced by templates over claim-graph statuses and registered check types (contract 44). A model may supply nothing displayed on layer 1 except a quoted span from the person's own text.
- The same view model feeds the HTML, the screen-reader text, the share card and the API, so the four cannot differ (contract 54).

## 2. Stack and rendering (ADR-010)

- **React 18 with TypeScript and Vite**, as decided earlier; **React Aria Components** (Apache-2.0) for primitives that carry difficult behaviour (dialogs, tabs, disclosure, menu buttons, tables with sortable headers). Phoenix, a rival-class observability product, uses React Aria and still ships focus-ring and keyboard regressions in tables and editors (market-intelligence report, section 6.2), so a library is a starting point and our own tests decide.
- **Today is served from a precomputed JSON document** (contract 33) rendered on the server at publish time into static HTML plus a small hydration bundle; opening the page makes no investigation, no model call and no RYO call. The page therefore works with JavaScript slow or off for reading; interactive controls (check a claim, follow, challenge) progressively enhance.
- **Level 2 (thesis page)** is a route rendered from the stored thesis record; checks arriving live are delivered over server-sent events into a polite live region (section 5), with the last good state as fallback.
- Charts only on level 2, drawn from the same data object as their accessible table and marker list; Lightweight Charts is a candidate renderer with a decorative canvas (its source has no ARIA or keyboard handling), or plain SVG generated by us; decided by the chart test in `ACCESSIBILITY_SPEC.md`.

## 3. Lints and the page test as build steps

| Lint (static, on view models and templates) | Rule | Evidence |
|---|---|---|
| Word budgets | per slot, per card, as amended by CF-17 (slots ≤ 14 words, meta ≤ 12 words, featured total counted over everything visible) | `card_lint.py` (E11): the contract's example featured card is 60 words, the shortened one 53; the lint caught a state chip written where an uncertainty chip belonged |
| Closed lists | state chips, uncertainty chips, trust phrases | same |
| Banned vocabulary | arm names, node, commitment codes, Brier, Holm, sensitivity, timing class, provenance level, badge names | same: it rejected "6 claim nodes ... commitment C3" |
| Generic labels | More, Details, Learn more, Open analysis, View | same |
| Causal and verdict wording | the lists of contract 35.2 and 48 and 55 | to build |

The **page test** (Playwright, three engines) runs on every route at 1440 x 900, 390 x 844 and 320 x 640: visible words in the first viewport counted as in E11 (words fully inside the viewport, with the partial count reported), the three-question test as a recorded human or reviewer answer, axe, console and page errors, horizontal overflow. Measured on the mock (E11): with the contract's own example copy, 167 words at 1440 x 900 and 106 (95 fully visible) at 390 x 844, which misses the 150 and 90 targets (CF-18); with the featured copy written to the budget (a next check of 8 words instead of 14) and slightly looser spacing, 136 fully visible words at 1440 x 900 (151 counting partial lines) and 88 at 390 x 844, 66 at 320 x 640. In both versions: zero axe violations, zero incomplete results, no horizontal overflow, no console error and a visible 3 px focus outline on every control in tab order. The lesson for the build is that the budget is met by writing short copy, not by hiding content.

## 4. States every screen must render (and the tests)

Empty (no data yet), loading with a skeleton of the real shape, partial (some checks done: the preliminary page), stale (last good result with its age), source unavailable (named source, what is affected, what still works), error (a specific message and a retry that does not lose input), and offline recorded mode (labelled *recorded*, never styled as live; the data mode and `as_of` of every number). Each state has a fixture and a screenshot test in light and dark; none may show a number without its freshness and mode.

## 5. Updates while reading

New checks arriving on level 2 are inserted in a fixed order below the current focus, announced politely (`role="status"`, not `alert`, WCAG 4.1.3), never move focus, never reflow content the reader is in the middle of (new items append; changed items mark `aria-busy` during replacement), and a node status that was `DONE` never changes silently: a change is a visible revision with its reason (contract 35.5, 52). A banner that is sticky must never cover the focused control (WCAG 2.4.11).

## 6. Navigation and labels

Four destinations beyond Today and the thesis page, each reached on purpose: Receipts and Verify, the Track Record, the Laboratory, and *More views* (the Screener, News, Indicator, Voices and Whales views, each carrying its gate label until it passes; the Drill page and the Evidence of quality page sit under Receipts and Verify on the judge path). Labels come from a label table (a tree test with 10 or more unfamiliar users targets 80 percent correct, a prior). The page title and the one `h1` state the page's purpose (the three-question test, question a).

## 7. Performance and delivery

The first screen is the static document; no web font blocks text (system fonts first); images are decorative or absent on layer 1; two budgets with their scopes: at most 100 KB of JavaScript before interaction on Today (a prior) and at most 200 KB on the whole initial route (the plan's figure), both counted as bytes a server sends (gzip level 6, one kilobyte = 1,000 bytes) and both measured on the built site by `web/tools/budget_test.py`: the pages that the first screen does not need are loaded when their link is followed, and the verifier is loaded when a bundle is checked. The measure is not yet a CI gate. Hosting and caching follow `OPERATIONS_ARCHITECTURE.md`.

## 8. Failure modes

| Failure | Behaviour |
|---|---|
| Precompute job late | last good list with its age; never blank |
| Live channel drops on level 2 | the page stays readable at its last state, says updates paused, offers a reload |
| Hydration bundle fails | reading still works; controls fall back to links and forms |
| A view model with a field outside the contract | build fails |

Connection to the journey: Today is the entry to "one claim"; level 2 is where the autonomous investigation, challenge and timed record become visible.
