# Verification specification

Scope: time-stamp assurance, verifier, timing levels, offline bundle. Status: DESIGNED; both verifier implementations (Python, JavaScript) exist as spikes (E2c) with <!--n:e2c-->48<!--/n--> cases agreeing; the timestamp token verifier (E2b) was run against nine live authorities. Product rules: contract sections 8, 11, 24, 26. This document defines what a verifier computes and what it may say. Built since: the token verifier, the trusted-root client, the timing rules and the offline bundle verifier are product code in Python and in Node and TESTED, with command-line verifiers (see `../STATUS.md`); revocation checking, C4 and witnesses are not built.

## 1. The verdict has four parts that are never merged

1. **Integrity:** the bytes are the bytes that were committed (record canonical form, leaf hash, inclusion proof to a checkpoint whose signature verifies under the policy's log key).
2. **Timing:** the level reached (C0 to C4) and the timing-assurance class (TA-1, TA-2, TA-3), computed from the tokens.
3. **Eligibility:** whether the record counts for a table (for example C3 or above and the eligible-after rule of contract 2), a separate output so a strict reader can apply a stricter rule.
4. **Not proven:** a standing list that is part of the output (the research content is true; the model reasoned this way; completeness before the first append; both authorities honest at once; the clock of the machine that ran the verifier).

A verifier prints all four; a summary badge is not an output.

## 2. Inputs and what the verifier trusts

Input: a bundle directory (ledger spec section 6) **and a trusted root supplied from outside the bundle** (an outside review: the first version read its trust anchors from the bundle's own `policy.json`, so an attacker could replace the records, the log key, the certificates and the policy together and every cryptographic check would pass against the substituted anchors). The trusted root holds the log origin and key (with the validity range of each key era), the pinned time-stamp root fingerprints, the **operator registry** (section 3, item 6), the algorithm allow-lists, the clock-offset limit and the witness set; it ships with the verifier release and is published through independent channels (the repository release, the first public checkpoint, and every later checkpoint note), and a verifier release is itself pinned by hash. This is the same shape as Sigstore's trusted root, a separate document with the log keys and the certificate and time-stamp authorities each carrying a validity range, distributed apart from the signed bundles (read in `sigstore_trustroot.proto`; the client documentation was not read). **The bundle's own `policy.json` is metadata: a difference from the trusted root is reported (`bundle_policy_differs`) and never believed.** Without a trusted root the verifier still checks self-consistency and time, and says so: `root_of_trust: BUNDLE_ASSERTED`, the level reads `C3-if-authentic (UNAUTHENTICATED)`, `scorable` is false, and the standing "not proven" list gains "that this bundle came from Hoshitori". **Succession:** a new policy version (key rotation, a new operator) is a record in the log signed by the previous key and carried in a trusted-root update; a verifier pinned at the genesis root can follow the chain and refuses an update that is not signed by a key it already trusts (designed, not implemented). The verifier never fetches anything; the machine clock is used for nothing but the report header (and an expiry check on the trusted root, which is reported separately).

**Trusted-root lifecycle (review 21; ADR-028; E24).** The trusted root is a chain of versioned documents modelled on The Update Framework's root update (specification section 5.3, read in full). Version N+1 is accepted only if a threshold of version N's root keys and a threshold of its own keys signed it (each key counted once), its version is exactly N+1, and the chain is within a bound; only the final root's expiry is checked, against a time fixed at the start of the update. The documents are fetched from at least two independent channels; two different documents for one version give FORK and no update. The signed bytes are the payload itself (no canonicalisation is needed for the root). A verifier whose latest obtainable root has expired reports EXPIRED and is not scorable. The root carries the log-key eras: an era's key is valid from its first size and, once the era is closed, only up to its closing size. E24 (Python and Node, 23 cases, six planted mutations caught) covers: honest rotation chains, signatures from the old keys only or the new keys only, a signature below threshold, one key signing twice, a skipped or replayed version, forked channels, expiry of a root and of an intermediate root, a chain over the bound, a malformed document, an edited payload and whole-channel rollback. **Shown limit:** a verifier that can reach no newer root accepts a retired era beyond its closing size until its own root expires; the expiry period bounds that window.

**Epoch acceptance (ADR-025; E21).** A checkpoint is accepted only if it is consistent with every published checkpoint and, when signed under the key of epoch `e`, its size does not exceed `closing[e]` (null for the open epoch). A stale primary's checkpoints beyond the closing size, or inconsistent with the published chain, are rejected even though its signature is valid.

**Ownership evidence (ADR-029; E23; E2c).** An operator counts toward independence only if the registry entry's evidence is a structured record of a kind listed in the trusted root (`ccadb_ca_owner_of_record`, `operator_published_root`), has a reference, and names the SHA-256 of the root the token actually chained to. A string, an unlisted kind, an empty reference or evidence about another operator's root yields no parent and no independence. Independence here means different organisations of record; common ultimate ownership is not excluded (NOT VERIFIED).

**Layer-1 wording for C2 (CF-34).** A public reference is a claim offline, so the first-layer phrase is "Publication reported, not independently time-verified"; "Independently time-stamped" is reserved for C3 and above (it said "before the outcome window" until the claim was made exact: a bundle proves the records existed as written by the time-stamps, and does not yet hold the origin step that would show the window, see `D01_VERIFIER_CHANGES.md`).

**The basis of a verdict.** The timing part of every verdict carries `basis`: the root's own required operator count, counting window before and after the commit, attestation close, largest spread between tokens and uncertainty constant (null when no root was used). A loose root gives a loose pass, and the verdict now says which rules it was judged by; both verifiers print the same object, checked on the shared case list, and the Verify page states it under the findings.

## 3. Algorithm (as implemented in E2c)

1. Parse the checkpoint note; verify the Ed25519 signature line(s) against the **trusted-root** log key (key id from `SHA-256(name ‖ 0x0A ‖ 0x01 ‖ key)[:4]`); reject if the origin differs from the policy, if no accepted signature line exists, or if a cosignature quorum required by the policy is missing (then the level cap applies, not an integrity failure).
2. Take the tree size and root **from the verified checkpoint only**; the proof's own size is never used (E2a: a proof verified for size ±1 in 206 of 309 trials).
3. Check every hash is exactly 32 bytes; recompute the leaf hash from the canonical record bytes; verify the inclusion path with the RFC 9162 iterative algorithm; check the record is in canonical form (the record profile; non-canonical text fails integrity).
4. Check cited raw payloads: SHA-256 equals the stored `raw_sha256`; a missing payload is `NOT RECONSTRUCTIBLE` for the reconstruction check and does not affect integrity of the record itself.
5. For each time-stamp token: parse strictly; status must be granted; version and digest algorithm consistent; the message imprint equals SHA-256 of the **checkpoint note text** (not just its root); CMS digest and signature algorithm are in the allow-list (SHA-1 rejected); the signer certificate chain verifies to a pinned root with a time-stamping extended key usage (critical); the signer certificate was valid at `genTime`; archived revocation evidence, if present, is checked and reported (absent revocation evidence is reported, not hidden). **Nonce rule (CF-05, CF-35), stated once:** online at stamping the response must echo the request's fresh nonce; offline the archived token is bound by its message imprint to the committed checkpoint digest and by the trusted signer policy, and a nonce is checked only when the original request nonce is available and authenticated, which the bundle does not carry.
6. **Operator independence and the counting window (CF-22, CF-23, CF-29; model E16):** tokens are grouped by (root fingerprint, signer certificate fingerprint); two tokens sharing either count as one operator. **Distinct fingerprints do not establish distinct organisations** (an outside review): each pinned root maps, in the trusted root's **operator registry**, to an operator entry with a `parent` (the organisation that ultimately controls it) and `ownership_evidence` (a citation of the operator's own disclosure); tokens count as independent only if their entries have distinct parents **and** non-empty ownership evidence, and the same registry covers witnesses and public-log operators (the roles must not share a parent). E2c cases: two roots under one parent, and an entry without evidence, both fall below C3. **The registry now has real entries for five of seven operators** (E23: the public CA database for DigiCert, Sectigo, GlobalSign and Certum, Apple's own page for Apple; ADR-029), with the evidence level stated; SwissSign and FreeTSA have none, and ultimate ownership is not established; a registry entry without evidence makes that operator count for nothing, which is the conservative failure. `committed_at` and any declared `outcome_window_opens_at` are read **from the proven forecast record inside the tree**, never from an unsigned bundle file (the first E2c verifier read an unsigned `commit.json`; editing only that file turned a late bundle from below C3 to C3, `demo_old_hole.py`). A token counts only if its `genTime` lies in `[committed_at − 1 s, committed_at + 60 s]` (the 1 s is the local clock-offset limit of the domain model) and after the proven existence of the record; a token outside the window is reported and never counted, never moves `attested_at` and never lowers a level that two counted tokens support. C3 requires at least two counted tokens from distinct accepted operators, mutually within 5 seconds; the attestation closes when two counted tokens are in or at `committed_at + 90 s` (the 60 s window plus a 30 s retry window), and the origin is set only after the close. A repeated token or a token for a different checkpoint does not count; a token arriving after the close is stored and changes nothing.
7. Compute the level: C1 if the record verifies; **C2 is a claim, not a proof, offline**: a publication reference in a bundle (a URL and the expected content hash) says where the checkpoint was published, and nothing in the bundle shows that it was published there or when (an outside review). The verdict reports `public_commit: claimed` with the number of references and `authenticated_offline: 0`; an online check may later report `confirmed_now` (the content matches at the time of checking, with the platform's own reported time labelled unauthenticated); only a record that is itself authenticated and independently timed (a signed record whose digest is covered by counted tokens) would be `authenticated`. C2 never raises a level and never counts toward headline eligibility (only C3 and above do); C3 per item 6; C4 only if the trusted root's required witnesses cosigned the checkpoint and the public-log inclusion proof verifies (the witness set and the log are operators in the registry). Compute the timing class (section 4). E2c case: forged publication claims leave the level and `authenticated_offline` unchanged.
8. Print the four parts.

## 4. Timing-assurance classes (CF-03)

- **TA-1** requires the authority's own policy statement bounding accuracy to be read and archived in the bundle (`policy.json` references it). **No authority is TA-1 today:** the policy search found a stated ±1 s for one provider's qualified service but not a mapping to the public endpoint we use, so nothing is claimed.
- **TA-2:** a published empirical calibration per authority (distribution of `genTime` against our own send and receive times). E2b measured excursions of −0.91 to +0.01 s for GlobalSign over 12 requests; whole-second `genTime` resolution everywhere (no fractions in about 100 tokens). TA-2 needs a pre-registered calibration set; the spike is a first look, not that set.
- **TA-3:** the assumed constant `u` = 5 s plus the observed spread. Every forecast today is TA-3.

## 5. Revocation

OCSP and CRL URLs exist for the signer certificates tested (GlobalSign, SwissSign: OCSP status good at the time of the run). The stamping step archives the OCSP response (and the chain) in the bundle; the offline verifier checks the archived response if present. Without archived evidence the verdict shows `REVOCATION_NOT_EVIDENCED`; it does not fall back to a live fetch (an offline verifier must not depend on today's network). **Not verified:** OCSP stapling timing guarantees; behaviour when an authority's certificate is revoked after stamping (the archived evidence plus the other token keep the level; the record is re-labelled with the reason, never silently kept).

## 6. Fresh-run agreement and reconstruction (not part of the cryptographic verdict)

Reconstruction (rebuild a decision from stored inputs and stored model outputs) and fresh-run agreement are separate checks with separate outputs (contract 11). They need payloads we may withhold; the verifier reports `needs authorised access` rather than a pass.

## 7. Tests (verifier-level)

Added after review 21 (E2c now has <!--n:e2c-->48<!--/n--> cases in all): five evidence-structure cases (a bare string, an unlisted kind, an empty reference, evidence about another operator's root, an empty accepted-kind list); the happy paths now use operators with real ownership evidence (digicert with globalsign, sectigo with certum, globalsign with certum reach C3 in both verifiers); a pair in which one operator has no evidence (swisssign, freetsa) stays below C3. Added after review 20 and passing in both verifiers (E2c, <!--n:e2c-->48<!--/n--> cases in all): a whole bundle substituted with the attacker's own log key, policy and real fresh tokens fails integrity against the trusted root and reads `UNAUTHENTICATED` without one; a bundle forged offline with two self-made time-stamp authorities (own CA, own timestamping certificate) fails against the trusted root and reads `C3-if-authentic (UNAUTHENTICATED)` without one, which is exactly why a verdict without a trusted root must never be shown as a Hoshitori result; a bundle whose `policy.json` names another key but whose records are honest verifies against the trusted root and reports `bundle_policy_differs`; edits to the signed committed time or declared window fail integrity; two roots under one parent and an entry without ownership evidence fall below C3; forged publication claims change nothing. A malformed or hostile time string in a record crashed the Python verifier in the first run of these cases (empty output) and now yields no timely token; a crash on hostile input is a defect, never a pass.

E2c's <!--n:e2c-->48<!--/n--> cases are the seed (happy paths with three operator pairs, alias pairs, single and no token, SHA-1 signer, same token twice, a token of another checkpoint, eleven integrity edits, edits to the signed committed time and window, six timing cases, operator-registry cases, trust-root substitution and offline-forgery cases, forged publication claims, the operator rewrite). Additional required tests: both verifiers on the same 200 randomly mutated bundles must agree on every verdict part; a long (beyond 2^32 leaf index) synthetic proof; a checkpoint with extra unknown signature lines (ignored, reported); a policy past its validity; a bundle whose `genTime` precedes the record's own `created_at` (impossible ordering → timing fails); property test that no mutation of a passing bundle raises the level.

## 8. Failure modes

| Failure | Behaviour |
|---|---|
| Verifier crash or non-termination on hostile input | each parser has size and depth limits; fuzz suite; a crash is a defect, never "pass" |
| Disagreement between the two implementations | build fails; the stricter result is shown until fixed |
| Unknown algorithm | rejected with the name; never silently accepted |
| Policy missing | no verdict beyond "hash matches" and the standing list |

Connection to the journey: this is what the "one independently timed record" step uses when the visitor runs verification offline.


## Rules from an earlier study (reproduced against our spikes)

1. **Certificate path.** Every certificate in a token chain is checked for the basic-constraints CA flag, key usage (certificate signing for issuers, time stamping for the signer), unknown critical extensions and path length, and the same tokens are run through `openssl ts -verify` as a differential test. The Python spike accepted a time-stamp certificate issued by an ordinary TLS leaf, an unknown critical extension and an intermediate without certificate-signing usage; openssl rejected all three.
2. **Signer binding.** The signer identifier of the signature must match the certificate whose key verifies it; a certificate merely present in the token never counts. The Node spike counted one genuine token as two operators after another operator's public certificates were injected.
3. **Clock.** A timestamp without an explicit offset is rejected. The verdict is a pure function of the bundle, the trusted root and the fixed clock input; with a naive committed time the level changed with the verifier's time zone.
4. **Trusted-root client.** Thresholds are at least 1 and counted over distinct keys (one key under two key ids is one signature); an unknown `format_version` is rejected; a missing required field is a rejection, never a crash; both implementations return the same code for the same input, checked by a differential test over a generated corpus. The reproduced cases are in `tests/test_ss08_attacks.py`.
5. **Stated limit.** Operator independence is judged between certificate authorities of record. One party that holds time-stamping certificates under two roots counts as two operators; the Verify page says so.

**The cycle's whole batch (the `cycle` part of the verdict).** A cycle commits one batch: its records are submitted and appended together, so they are the last records of the log under the checkpoint that the time-stamps cover, and the cycle's COMMITTING step is the last of them. That step names `batch_size`, the number of records before it that make the batch, and `batch_root`, the Merkle root of the digests of those records (the stored record without the member the ledger's writer added, in log order). A verifier takes the records at the `batch_size` positions before the COMMITTING step, requires every one to be in the bundle with its own proof intact, and recomputes the root. The verdict prints `cycle.declared` (a committing step is in the bundle), `cycle.steps`, `cycle.batch_size`, `cycle.members_present` and `cycle.complete` (the recomputed root is the named one). A record left out, added or changed gives another root or a missing member; a size or root the records do not give leaves the bundle not complete. A bundle with no committing step shows nothing, and so does one with two (a bundle shows one cycle); both are not scorable, with the reason `COMPLETENESS_NOT_SHOWN` (placed after `UNRESOLVED_REFERENCE`). A bundle that holds no forecast (a cycle that made no call, or one whose calls were all left out) is not scorable either, with the reason `NO_FORECAST` (placed after `COMPLETENESS_NOT_SHOWN`, before `DATA_MODE`), and the verdict prints `eligibility.forecasts`, the number of forecasts present with their proofs intact: there is nothing to score in a bundle of evidence alone. **Stated limit:** the step is the operator's own record, so a writer that commits a smaller batch than it ran is complete as written; what the pass shows is that nothing was taken out *after* the commitment. The origin of each call's window and the settlement are written after the stamped checkpoint and are the next part of the stage (a later checkpoint with a consistency proof).

**The later part (the `cycle.later` part of the verdict, stage C parts 2 and 3).** A bundle may hold records the log appended after the stamped checkpoint: the steps of the cycle's forecasts (committed, waiting for the origin, open, ended), each proven under one later signed checkpoint, and `consistency.json` (the members `format` 1, `from_size`, `to_size` and `hashes`, in canonical form), the RFC 9162 path showing that the later tree extends the stamped one. A bundle shows at most two checkpoints. Both are held to the trusted root's eras; the tokens stamp the smaller one only, and the window rule applies to the records under it alone. A missing file leaves the checkpoints differing (`CHECKPOINTS_DIFFER`); a file that is present but wrong, or a path that does not verify, is `CONSISTENCY_FAILED`; three checkpoints are `CHECKPOINTS_DIFFER`. The verdict prints `integrity.checkpoints` (`stamped`, `later`, `consistency`: none, verified, failed or missing), `timing.later_items` and, per forecast of the batch, `cycle.later.forecasts.<id>`: the committed level, `awaiting` (the step that names the eligible time: ok, early, absent, conflicting, malformed or unchecked), the eligible time and the one derived from the tokens (the attested time plus the uncertainty plus the spread), `origin` (the opening step: ok when it is the first minute close after its own eligible time and not before the derived one; early, wrong, absent, conflicting, malformed or unchecked) and `ended` (the state of an ending step, never whether it is right). `cycle.later.failures` counts the forecasts whose eligible time or origin does not follow, and then the bundle is not scorable, with the reason `ORIGIN_BEFORE_ATTESTATION`. A bundle with no later part says nothing about origins and gains no reason; a bundle that is not intact shows no later part. The league exports the later part with the newest checkpoint its ledger has signed after the steps (at the next commitment, or when the writer stops), and a site export makes a bundle again when the log has signed a later one than it holds.

**A cited record that the bundle does not hold.** A record's `refs` name the records it read. A reference to a record that is not in the bundle is listed in `integrity.refs.unresolved`; it does not fail integrity, because what is present is intact, but the bundle is not scorable, with the eligibility reason `UNRESOLVED_REFERENCE`, because a forecast cannot be judged on evidence the bundle does not hold. The reasons are `ROOT_NOT_CURRENT`, `INTEGRITY`, `LEVEL_BELOW_C3`, `UNRESOLVED_REFERENCE`, `COMPLETENESS_NOT_SHOWN`, `NO_FORECAST`, `ORIGIN_BEFORE_ATTESTATION` and `DATA_MODE`, in that order, in both verifiers. This closes only the cited-record part; a forecast left out of a bundle, or a cycle's whole set, is the completeness check of the cycle's whole batch (below).
